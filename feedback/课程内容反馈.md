# 课程内容反馈

> 两轮：**pre01–pre02**（环境搭建 + Trace 实操）｜**ch01–ch02**（三层架构 + 快速上手）
> 下文标「实测」的，都是在本地 deepagents 0.7.8 / langchain 1.4.3 上跑出来或读源码看到的，不是印象。

---

## 第一轮 · pre01–pre02

### 做得好的地方

**1. 生命周期工具链的设计很扎实**

`create → info → task → doctor → dev` 这五个命令把「建项目、看要求、装依赖、查就绪、起服务」串成了一条线，而且每条都能单独跑、单独排错。`doctor` 在 `dev` 之前拦住未满足的条件（缺 key、缺目录）这个设计尤其好——比"先起来再说、跑一半才报错"省太多时间。

**2. 对版本不确定性写得很诚实**

pre01 里反复出现「本文命令于 2026-08-18 使用 AgentSeek 0.1.2 验证」「如果任务名称与本文不同，以 `agentseek task --list` 的输出为准」。我实际遇到的情况正是这样：main 分支的模板比教程多了一个 `course-check` 任务、`deepagents` 从 0.6 到了 0.7.8。教程提前说了，我就没有怀疑自己装错。

**3. pre02 的 Trace 实操是有真东西的**

「162 个 Run，22 个模型 Run，17 个工具 Run，最慢叶子 85.9 秒，最慢工具 25.1 秒」——这种带具体数字的参考值，让我能判断自己的结果是否合理（我跑到 46 个 LLM / 61 个 tool / 313 秒，量级一致）。而且教程明确写了「不要把根 Trace、task 子 Agent 包装或 middleware 包装层直接当成瓶颈」，这一句直接决定了我分析时没有把 282 秒的 `task` 误判成工具瓶颈。

**4. 安全提醒到位**

「不要把真实 Key 写进 Shell 命令，也不要使用 `--api-key`」——这条我在 `langsmith-trace` 的 SKILL.md 里也看到了同样的警告，两处一致，很容易形成习惯。

### 建议补充或修正的地方

**1. `tavily_search` 的返回内容没有长度上限（模板层问题）**

模板的 `fetch_webpage_content` 把整页 `markdownify` 之后原样返回，没有任何截断。实测一次深度研究会累积 **30 多个 `/large_tool_results/*`，单个 300 KB–1.4 MB，state 总计 23 MB**，前端加载时浏览器主线程直接卡死。

建议：在模板的 `tools.py` 里默认加一个 `MAX_PAGE_CHARS`（实测 8000 够用），或者在 pre01 加一句提示。这个不是学员能自己想到的。

**2. SSE 断开后 run 状态不更新（`agentseek-api` 层问题）**

研究中途刷新页面、或者浏览器把标签冻结，SSE 一断，后端图会继续跑完，但 run 状态永远停在 `running`，前端就一直转圈。实测三次，每次都要手动 `POST /threads/<tid>/runs/<rid>/cancel` 才能看到已生成的结果。

建议：在 pre01「运行期间请保持 `agentseek dev` 和前端页面打开」这一句后面，补充「**如果中断后页面一直转圈，说明 run 状态卡在 running；先 cancel 再刷新，数据不会丢**」，并把 cancel 命令给出。

**3. 没有提醒浏览器后台标签会被冻结**

这是上面第 2 条最常见的触发原因。Chrome 会把后台标签的定时器降到 1 次/分钟，长时间无交互直接 freeze。教程只说「保持页面打开」，容易让人以为「切到别的标签也算打开」。

建议改成：「**运行期间请保持页面在前台标签可见**，切到其他标签会导致流式连接中断」。

**4. Node/npm 的版本建议可以更具体**

教程写「Node.js、npm 当前 LTS 版本」。实测 Ubuntu 26.04 apt 里的 npm 是 9.2.0，`npm install` 在解析 vitest 这类嵌套 peer 依赖时会崩：

```
npm ERR! Cannot read properties of null (reading 'edgesOut')
```

升级到 npm 11 后正常。建议补一句「npm ≥ 10；如果遇到 `edgesOut` 报错，先升级 npm」。

**5. pre02 的「编码助手」前提假设偏强**

pre02 全程假设学员有 Codex / Claude Code / Cursor。如果没有（比如我），第 1–3 步和 6–7 步能跑，但第 4、5 节的核心实操（让编码助手读 SKILL.md 然后执行）就没有载体。

建议加一句替代方案：「没有编码助手时，可以直接阅读 `.agents/skills/<name>/SKILL.md` 并按其中的 reference 文件自查，或把 SKILL.md 内容贴给你使用的任意 LLM 工具」。

### 第一轮总体评价

内容质量高于我预期，尤其是「命令解释」和「版本不确定性提示」这两块，明显是有真实踩坑经验的人写的。上面五条建议集中在两个方向：**模板的默认值应该更保守**（有没有截断、有没有上限），以及**故障恢复路径要写进正文而不是留给学员自己查**。

如果要我只留一条建议：**把「页面卡死怎么判断是后端挂了还是前端挂了」写成一节**，给出 `/state` 和 `/runs` 两个接口的查法。这是我这次花时间最多、也最没有外部资料可查的一段。

## 第二轮 · ch01–ch02（Task2）

### 做得好的地方

**1. 「三层是叠上去的，不是竞争关系」这句话是整章的定海神针**

我在读之前对 LangGraph / LangChain / Deep Agents 的关系是糊的，一直以为要选一个。ch01 用「工作台 / 锤子锯子 / 装好的工具间」这个比方，加上「三者可以组合使用」那一段，一次就把这件事掰正了。后面再看 `create_deep_agent()` 内部调 `create_agent()` 再落到 LangGraph，就完全不意外。

**2. 表格里那句「默认 claude-sonnet-4-6，但依赖隐式模型已弃用」，实测完全准确**

我特意去读了源码：`model=None` 时走 `get_default_model()` → `ChatAnthropic(model_name="claude-sonnet-4-6")`，而这个函数上挂着 `@deprecated(since="0.5.3", removal="1.0.0")`。**连废弃的版本号都写对了。** 这种「不糊弄版本细节」的写法让我敢信这张表。

**3. 「v0.7 默认基础提示词为空」实测准确到字符级**

我传 `system_prompt="test"`，用间谍模型截了实际发给模型的 system message——**就是 4 个字符的 `test`**，一个字没多加。这条如果写模糊了（比如写「有少量默认提示词」），学员会永远搞不清自己的 token 花在哪。

**4. 「文件系统 7 个工具」这个数字是对的**

`FilesystemMiddleware` 里定义了 8 个（多一个 `execute`），但默认绑定给模型的确实只有 7 个文件工具 + `task` = 8 个。课程表格写 7 个，和实际行为一致，不是照抄中间件定义。

**5. 用 `MODEL_NAME` 环境变量管理模型名，这个设计很省事**

课程所有示例都是 `os.environ.get("MODEL_NAME", "Qwen/...")`，换模型不用逐处改代码。我实际用 DeepSeek 端点跑，改一个变量就切过去了。

**6. 明确写了「初次阅读可先跳过研究助手那节」**

这个提示很实用。ch02 后半段（Tavily + TodoListMiddleware）对刚学完 Hello World 的人来说信息量确实大，课程自己承认这一点并给了跳过许可，比硬着头皮读完效果好。

### 建议补充或修正的地方

**1. 「默认基础提示词为空」这句话容易被误解，建议补一句限定**

实测：不加中间件时 system message 确实只有你自己写的那句（4 字符）；但**加了 `TodoListMiddleware` 之后，system 会变成 1376 字符**——多出来的 1372 字符是中间件注入的 `## write_todos` 使用说明。

也就是说「空」指的是 **Harness 不主动注入**，不是「模型看不到 system message」。这两件事差别很大：前者是设计取向，后者是事实错误。

建议改成：**「v0.7 默认不注入任何基础提示词；你写什么模型就看到什么。注意中间件会按需追加内容——例如启用 `TodoListMiddleware` 会给 system 增加约 1.4 KB 的工具说明。」**

**2. `execute` 的缺席没有解释，学员会以为「Agent 不能跑代码」**

ch01 的能力表写「虚拟文件系统：7 个文件操作工具」，ch02 也没提 `execute`。但 `FilesystemMiddleware` 源码里其实有 8 个工具（含 `execute`），只是**默认的 `StateBackend` 不支持执行命令，所以不绑定**。

我实测默认工具列表是：

```
['ls', 'read_file', 'write_file', 'edit_file', 'delete', 'glob', 'grep', 'task']
```

没有 `execute`。如果学员照着教程让 Agent「跑一下这段代码」，它会说不会——但教程没解释为什么。

建议在 ch01 的能力表加一列「默认可用 / 需配置」，并在 `execute` 后面标注「需支持执行的 Backend（如 `LocalShellBackend` 或沙箱），见第 10 章」。

**3. `create_deep_agent()` 的参数表只列 3 个，但没说「一共 18 个」**

我 `print(inspect.signature(create_deep_agent))` 出来是 **18 个参数**（`model` / `tools` / `system_prompt` / `middleware` / `subagents` / `skills` / `memory` / `permissions` / `backend` / `interrupt_on` / `response_format` / `state_schema` / `context_schema` / `checkpointer` / `store` / `debug` / `name` / `cache`）。

课程表格只讲 3 个，这个取舍是对的（避免第一课就劝退），但**建议加一句**：「完整签名还有 15 个参数，分别是后续第 3–16 章的入口，现在不用管」——否则学员自己 `help()` 一下会懵。

**4. 中间件的装配顺序没给，但这是理解「谁先改请求」的关键**

ch01 说「Middleware 提供能力并控制执行环节」，ch02 说「Middleware 让循环具备 Harness 能力」，但两章都没给出**实际顺序**。我读 `graph.py` 的 docstring 拿到了完整顺序：

```
Base:  SkillsMiddleware(if skills) → FilesystemMiddleware → SubAgentMiddleware(if subagents)
       → SummarizationMiddleware → PatchToolCallsMiddleware → AsyncSubAgentMiddleware(if async)
User:  你传的 middleware=[...] 插在这里
Tail:  profile extra → _ToolExclusionMiddleware → Anthropic/Bedrock/Fireworks PromptCaching
```

这个顺序不是细节——它决定了「上下文压缩」和「你的中间件」谁先看到请求。建议在 ch01「各项能力分别由谁负责」那张表后面补一张顺序图。

**5. LangSmith 那段没说「区域选错 = 静默失败」**

课程说了「只保留一个生效的 Endpoint」「URL 末尾不要加 `/`」，也说「如果 Trace 没出现，先核对区域」。但没明说失败的表现形态：

> **代码完全跑通、日志一切正常、LangSmith 里就是没有这条 Trace。**

我第一轮踩过这个，当时以为是 key 失效，查了半小时。建议直接写成一句：「**区域不匹配不会报错，只会让你在控制台里看不到 trace**」。

**6. 「LangChain 1.0」应改成「LangChain 1.x」**

我 `pip install "deepagents>=0.7,<0.8"` 装出来是 **langchain 1.4.3**。课程说「LangChain 1.0 构建在 LangGraph 之上」，大版本对，但小版本已经到 4 了。学员如果按「1.0」去搜 API 文档，可能对不上。建议改成 1.x，或者加一句「以实际安装版本为准」。

**7. ch01 的 `graph.py` 链接钉在 `deepagents==0.7.1`，和课程要求的版本范围不一致**

课程要求 `deepagents>=0.7,<0.8`，实际装到 0.7.8；但源码链接指向 `deepagents%3D%3D0.7.1` 那个 tag。学员照着链接去对行号，会发现和本地文件对不上（我这边的 `graph.py` 就比 0.7.1 长了不少，多了 `HarnessProfile`、`_excluded_middleware`、`RubricMiddleware` 这些）。

建议：链接改指 `main` 分支，或者加一句「链接是 0.7.1 的，你本地可能是 0.7.x 的更高版本，函数名一致但行号会漂」。

**8. ch02 的「三要素」讲得很好，但可以补一句「`Literal` 是给模型上锁」**

课程讲了参数类型标注、docstring、默认值，也讲了 `Literal` 的写法，但没点破它在 JSON Schema 里的作用。实测：

```python
topic: Literal["general","news","finance"] = "general"
```

翻译成：

```json
"topic": {"default": "general", "enum": ["general","news","finance"], "type": "string"}
```

**`enum` 是一道硬约束**——模型只能在这三个值里选，不会传 `"tech"`。而写成 `topic: str` 就没有这个保护。这一条对写工具的实际收益，比「类型标注」本身还大。

建议在三要素表格后面加一行：「`Literal[...]` → `enum`，把模型的取值空间锁死」。

### 第二轮总体评价

ch01 的概念密度高但骨架清楚，ch02 的实操路径短平快，两章配合得好——**先讲「为什么有三层」，再讲「怎么用最上面那层」**，顺序没毛病。

我这轮最大的收获不是「跑通」，而是发现**课程里那些可以核实的断言，我全都能在本地源码里对上**（默认模型、默认提示词、默认工具数、TodoListMiddleware 的开关差异）。这说明作者是照着真实代码写的，不是照着别的博客转述的。

上面 8 条建议集中在三类：

1. **该说清边界的没说清**（`execute` 为什么没有、`model` 为什么必须传）
2. **该给数字的没给数字**（中间件顺序、默认提示词长度、参数总数）
3. **版本细节会漂**（1.0 vs 1.x、0.7.1 的链接 vs 0.7.8 的本地）

如果只留一条：**把「默认给了什么、没给什么」做成一张表放在 ch02 开头**——默认 8 个工具、默认 system prompt 就是你写的那句、默认 backend 是 `StateBackend` 所以不能执行命令。学员拿到这张表，后面所有「为什么它不……」的问题都能自己回答。
