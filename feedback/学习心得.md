# 学习心得

## 一、为什么选 WSL2 而不是原生 Windows

课程建议 Windows 学员优先用 WSL2，我一开始想省事，直接在 PowerShell 里装。结果卡在一个很具体的地方：`agentseek-api` 启动即崩，报 `Embedded Client is not available`。查下去发现根因是 `pylibseekdb` 只有 Linux 的 wheel，Windows 上装不了。

这件事教会我一条：**报错信息里的关键词比任何教程都可靠**。我没有继续在 Windows 上折腾绕过方案，而是回头装了 WSL2 Ubuntu，一次性解决了这个类问题——后来 `pylibseekdb==1.4.0.post1` 在 Linux 上一次装成功，就是最直接的验证。

顺带补上了几个一直没搞清的概念：WSL2 是共享一个 Linux 内核、各自挂独立根文件系统的两个发行版（我的机器上 `docker-desktop` 和 `Ubuntu` 并列，`uname -r` 一模一样）；`networkingMode=mirrored` 让 WSL 和 Windows 共享 loopback，所以能在 Linux 里直接访问 Windows 的 `127.0.0.1:7897` 代理；WSL 默认发行版常是 Docker 注册的那个，`wsl -l -v` 里的 `*` 决定不带 `-d` 时进哪里。

## 二、AgentSeek 的生命周期设计

`.agentseek/lifecycle.toml` 是我这次最想记住的东西。它不是脚本，是一份**声明式清单**：要哪些命令、哪些环境变量、哪些文件、起哪些进程、怎么判断服务活着。`info` 读它展示、`doctor` 读它校验、`task` 读它执行一次性任务、`dev` 读它启服务。

这个设计的实际好处是：命令要在项目目录内执行（它从当前目录向上找 `lifecycle.toml`），所以我在 `~` 下跑 `agentseek task sync` 直接报 `Missing AgentSeek lifecycle spec`。一开始觉得麻烦，想明白之后反而觉得对——**环境要求是数据，工具才能统一校验**，比一堆散落的 shell 脚本可靠。

## 三、三个「卡死」教会我诊断

整个过程我遇到三次页面卡死，但根因完全不同，这是我这次收获最大的一段。

**第一次**：页面完全无响应。查 `GET /threads/<id>/state` 发现 state 有 **23 MB**，里面 30 多个 `/large_tool_results/*`，每个 300 KB–1.4 MB。根因是模板的 `tavily_search` 把整页网页 `markdownify` 后原样返回、**没有长度上限**，30 次搜索累计 20 MB，浏览器主线程解析就死了。修法是加一行 `MAX_PAGE_CHARS = 8000` 在 `fetch_webpage_content` 里截断——**逻辑不动，5 行代码**。

**第二次**：一直转圈 "Research in progress"。这次数据只有 160 KB，不是大小问题。查 `GET /threads/<id>/runs` 发现 run 状态卡在 `running`，同时 `next: []`、`todos` 全 `completed`——**图早就跑完了，只是状态机没收尾**。根因是跑到一半刷新页面导致 SSE 断开，`agentseek-api` 0.2.3 不把中断的 run 更新为 `success`。修法是 `POST .../runs/<rid>/cancel`，状态变 `error` 后刷新就能看到全部结果。

**第三次**：我以为"放后台应该没事"，结果又卡。这次学到的是浏览器行为：**Chrome 会冻结后台标签**（定时器降到 1 次/分钟、长时间无交互直接 freeze），SSE 长连接被挂起，前端就再也收不到结束信号。结论很硬：**这个模板跑研究时必须保持标签在前台**。

三次排查的共通方法是：**不要看页面猜，去查 API**。`/threads/<id>/state` 的 `values.messages` 条数、`values.todos` 状态、`next` 字段，加上 `/threads/<id>/runs` 的 status，三条证据就能判断「还在跑」还是「早跑完了前端挂了」。这个判断顺序救了我至少两次不必要的重跑。

## 四、Trace 分析推翻了我的直觉

我原以为慢在网络或者模型排队。打开 LangSmith 拿到 trace 一算：**总耗时 313.49 秒，其中 46 次 LLM 调用合计 275.8 秒，占 88%**。

更细的发现是：最慢那次调用 38.78 秒，但 `start` 到 `first_token` 只差 **1 秒**——也就是说瓶颈不是"等首字节"，是**吐字本身慢**（那次输入 80,090 tokens，输出是最终报告全文）。这直接改变了优化方向：调超时没用，要砍输入或缩短输出。

工具侧也很清楚：`tavily_search` 26 次共 195 秒，是唯一有实际耗时的工具；`grep`/`read_file`/`edit_file` 27 次合计 0.05 秒，完全不是问题。而看起来最慢的 `task`（3 次、282 秒）是**子 Agent 包装层**，不能当工具瓶颈——它内部还有自己的模型和工具调用，重复计算了。

## 五、最大的收获

不是"跑通了一个 Agent"，而是**建立了三个习惯**：

1. **先看数据，再下结论**——页面卡不等于服务挂，`state` 和 `runs` 两个接口就能分开。
2. **改一行能修的就别改十行**——`MAX_PAGE_CHARS` 一个常量解决了 20 MB 的问题。
3. **记录环境和版本**——`npm 9.2.0` 解 peer 依赖崩 `edgesOut`，升到 11 就好；这类问题不写下来，下次还得重新查一遍。

课程给的是一条能跑的路径，真正学到的能力是在它跑不通时能定位到哪一层出了问题。

## 六、Task2 让我改掉的一个坏习惯：不再「相信」，改成「打印出来看」

ch01 有一句话，我第一遍读的时候直接划过去了：**「`create_deep_agent()` 内部调用 `create_agent()`，最终由 LangGraph 执行。」**

这句话很好懂，所以我信了。但这次我多做了一个动作——只加了两行：

```python
print(type(agent).__name__)      # CompiledStateGraph
print(list(agent.nodes.keys()))  # ['__start__', 'model', 'tools', 'PatchToolCallsMiddleware.before_agent']
```

**两行输出，把这章最重要的一句话从「我记得文档这么说」变成了「我看到的就是这样」。**

`CompiledStateGraph` 是 LangGraph 的类，不是 Deep Agents 的类——说明 Harness 没有另造运行时，它就是把图配好再编译。而 `nodes` 只有 4 个：开始、调模型、跑工具、补参数。**我原以为「三层架构」是一堆代码，结果底下就 4 个节点。**

这件事教会我一个可以复用的判断：**文档里凡是「内部调用了 X」这种话，都可以用 `type()` 或 `inspect.getsource()` 花 10 秒钟验一下。** 验完再往下读，心里是实的。

## 七、docstring 不是写给人看的

我以前的认知是：docstring 是给同事看的注释，写差点也不影响运行。

ch02 让我彻底改了这个想法。我把课程里的 `calculate` 丢给 `convert_to_openai_tool()`，看它翻译成了什么：

```python
def calculate(expression: str) -> float:
    """Evaluate a math expression and return the result.

    Args:
        expression: A math expression, e.g. "1 + 2 * 3".
    """
```

↓

```json
{
  "name": "calculate",
  "description": "Evaluate a math expression and return the result.",
  "parameters": {
    "properties": {
      "expression": {
        "description": "A math expression, e.g. \"1 + 2 * 3\".",
        "type": "string"
      }
    },
    "required": ["expression"]
  }
}
```

**模型永远看不到函数体，它只看到这段 JSON。** docstring 第一行变成「什么时候调我」，`Args:` 段变成「每个参数填什么」，类型标注变成 `type`，默认值变成 `default` 并从 `required` 里消失。

所以我以前觉得「写清楚 docstring」是代码洁癖，实际上是**在写模型唯一的说明书**。写得含糊，模型就会用错——而我还以为是模型笨。

最让我意外的是 `Literal`：

```python
topic: Literal["general","news","finance"] = "general"
```

它翻译成 `"enum": ["general","news","finance"]`。**这是一道硬锁**——模型只能在这三个值里选，不可能传 `"tech"`。而写成 `topic: str` 就没有这个保护。

这让我重新理解了「约束模型」这件事：不是靠 prompt 里写「你只能选这三个」，而是**在 schema 层把它锁死**。前者靠模型自觉，后者靠接口强制。

## 八、「默认值」是要算账的

ch02 说 v0.7 把任务规划改成按需启用，「短任务不用为计划工具和提示词支付固定成本」。

这句话我第一遍读也是划过去。后来我对比了开关前后：

| | 不加 `TodoListMiddleware` | 加了 |
|---|---|---|
| 工具数 | 8 | 9（多 `write_todos`） |
| system message | **4 字符** | **1376 字符** |

**多付了 1372 个字符，每次请求都要付。**

这让我第一次对「上下文是有成本的」有了具体感觉。以前我理解的成本是「token 要花钱」，现在的理解是：**每一个中间件、每一个工具，都在每一轮对话里向你收一笔固定的「上下文税」。** 短任务根本不需要计划工具，那就别开。

同样的事也发生在「默认给了什么」上。我实测默认工具是：

```
['ls', 'read_file', 'write_file', 'edit_file', 'delete', 'glob', 'grep', 'task']
```

8 个。里面**没有 `execute`**——因为默认后端 `StateBackend` 把文件存在 state 里，根本没法执行命令。这解释了我之前的一个困惑：为什么有些教程里的 Agent 能跑代码，我的不能。**不是配置错了，是后端不支持。**

## 九、一个我刻意没做的事

这轮我**没有跑完整的 Hello World**，也没接 Tavily。

不是我偷懒，是我想验证一件事：**能不能在不花一分钱、不发一次网络请求的前提下，把「模型到底收到了什么」搞清楚？**

能。办法是写一个「间谍模型」——继承 `BaseChatModel`，在 `bind_tools` 里把工具列表抄下来，在 `_generate` 里把消息抄下来，然后返回一句假回答。这样整个 Agent 图会完整跑一遍（中间件全部执行），但请求根本没发出去。

```python
class Spy(BaseChatModel):
    @property
    def _llm_type(self): return "spy"
    def bind_tools(self, tools, **kw):
        CAP["tools"] = [t.name for t in tools]
        return self
    def _generate(self, messages, stop=None, run_manager=None, **kw):
        CAP["msgs"] = list(messages)
        return ChatResult(generations=[ChatGeneration(message=AIMessage(content="done"))])
```

这个手法我觉得比跑通一次 API 更有价值：**它把「Agent 框架」和「模型服务」彻底解耦了。** 以后调试任何 LangChain 系的 Agent，都可以先用它看一眼「我到底发了什么」，确认无误再花钱调真模型。
